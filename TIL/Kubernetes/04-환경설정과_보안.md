## 🦐 Namespace — 클러스터 안의 논리적 구획

Namespace는 하나의 물리적 클러스터를 여러 개의 논리적 "가상 클러스터"처럼 나눠 쓰게 해주는 격리 단위다. 실제 자원(노드의 CPU/메모리)을 물리적으로 분리하는 게 아니라, 이름 기준으로 리소스를 그룹핑해서 관리 편의성을 주는 개념 — **폴더**처럼 생각하면 쉽다.

왜 필요한가: 팀별/환경별(dev, staging, prod)로 리소스를 나눠 관리하고 싶을 때, 이름 충돌 없이 같은 이름의 리소스(예: `nginx-deploy`)를 서로 다른 namespace에 각각 만들 수 있다. 그리고 이 도메인의 다른 항목들 — ResourceQuota, RBAC(인가) — 은 대부분 **namespace 단위로 스코프**된다. 즉 Namespace 개념을 먼저 잡고 가야 나머지 항목들이 이해하기 쉬워진다.

### 기본 제공 Namespace 4가지

| Namespace | 용도 |
|---|---|
| `default` | 명시적으로 지정하지 않으면 리소스가 여기에 생성됨 |
| `kube-system` | 쿠버네티스 자체 컴포넌트(kube-dns, kube-proxy 등 시스템 Pod) |
| `kube-public` | 클러스터 전체에 공개로 읽히는 리소스 (인증 없이도 조회 가능) |
| `kube-node-lease` | 각 노드의 heartbeat(lease) 오브젝트 — 노드 상태 감지용 |

### 🦐 Namespace-scoped 리소스 vs Cluster-scoped 리소스

모든 리소스가 namespace에 속하는 건 아니다.

| 구분 | 예시 | 확인 명령어 |
|---|---|---|
| Namespaced (특정 namespace 소속) | Pod, Deployment, Service, ConfigMap, Secret, Job, ReplicaSet | `kubectl api-resources --namespaced=true` |
| Cluster-scoped (namespace 없음, 클러스터에 전체 1개) | Node, PersistentVolume, ClusterRole, ClusterRoleBinding, Namespace 자신 | `kubectl api-resources --namespaced=false` |

> 💡 실전 포인트: `kubectl get pod nginx-pod`가 "not found"로 나온다고 리소스가 진짜 없는 게 아닐 수 있다 — 다른 namespace에 있는데 `-n` 없이 조회해서 `default`에서만 찾다가 못 찾은 경우가 매우 흔하다. "리소스가 안 보인다"는 문제의 절반은 namespace 확인부터 시작하면 된다.

### Namespace 관련 명령어

```bash
# 생성
kubectl create namespace dev
kubectl create ns dev                            # 축약형

# 조회
kubectl get namespaces                            # 전체 namespace 목록
kubectl get pods -n dev                            # 특정 namespace 안의 Pod만 조회
kubectl get pods --all-namespaces                   # 전체 namespace 통틀어 조회
kubectl get pods -A                                  # 위와 동일 (축약)

# 생성 시 namespace 지정
kubectl run nginx-pod --image=nginx -n dev
kubectl apply -f pod.yaml -n dev

# 현재 컨텍스트의 기본 namespace 자체를 바꾸기 (매번 -n 안 쳐도 되게)
kubectl config set-context --current --namespace=dev
kubectl config view --minify | grep namespace:      # 현재 기본 namespace 확인

# 삭제 (⚠️ 그 안의 모든 리소스가 함께 삭제됨)
kubectl delete namespace dev
```

```yaml
# namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dev
```

### 🦐 Namespace 간 통신 — DNS 이름에 namespace가 포함된다

[[05-서비스와_네트워킹|Service]]는 클러스터 내부 DNS로 `<서비스이름>.<namespace>.svc.cluster.local` 형태의 주소를 받는다. **같은 namespace 안에서는 서비스 이름만으로 접근 가능**하지만(`nginx-svc`), **다른 namespace에 있는 서비스를 호출할 때는 namespace까지 붙여야 한다**(`nginx-svc.dev.svc.cluster.local`, 짧게는 `nginx-svc.dev`).

> ⚠️ 흔한 함정: frontend Pod가 `dev` namespace에, backend Service가 `prod` namespace에 있는데 frontend 코드에서 그냥 `backend-svc`로만 호출하면 연결이 안 된다 — 같은 namespace가 아니라면 namespace가 포함된 풀네임이 필요하다.
