## 🦐 계층 구조 한눈에 보기

```
Deployment  ─(관리)─▶  ReplicaSet  ─(관리)─▶  Pod × N
   │ 선언적 업데이트/롤백을 위해 ReplicaSet을 감쌈
                              │ 지정된 개수의 Pod를 유지(self-healing)
                                          │ 실제 컨테이너가 도는 최소 배포 단위 ([[01-애플리케이션_설계와_빌드]] 참고)
```

보통 실무/시험에서는 Pod나 ReplicaSet을 직접 만들지 않고, **Deployment 하나만 다루면 나머지는 자동으로 따라온다.**

## 🦐 ReplicaSet — 개수 보장 컨트롤러

- **지정된 수(replica)의 Pod가 항상 떠 있도록 보장**하는 컨트롤러. Pod가 죽으면 즉시 새 Pod를 만들어 채운다 (self-healing).
- `spec.selector.matchLabels`로 "어떤 라벨을 가진 Pod를 관리할지" 정의하고, `spec.template`으로 "새로 만들 Pod의 모양"을 정의한다.
- 시험/실무에서 ReplicaSet을 직접 만드는 일은 드물다 — Deployment가 내부적으로 자동 생성·관리한다.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

```bash
kubectl get rs                       # ReplicaSet 목록
kubectl describe rs nginx-rs         # 상세 (DESIRED/CURRENT/READY 확인)
kubectl scale rs nginx-rs --replicas=5   # 수동 스케일 (Deployment 없이 직접 조작 시)
```

> ⚠️ 헷갈리기 쉬운 포인트: `replicas` 개수를 3 → 1로 줄이면 ReplicaSet은 **아무 Pod나 골라서** 종료시킨다. 특정 Pod를 지켜야 한다면 `matchLabels` 조건에서 벗어나게 라벨을 바꾸거나 별도 전략이 필요하다.

## 🦐 ReplicaSet YAML 치트시트

```yaml
apiVersion: apps/v1          # ⚠️ 반드시 apps/v1. "v1"로 쓰면 no matches for kind 에러
kind: ReplicaSet
metadata:
  name: myapp-replicaset
  labels:
    app: myapp
spec:
  replicas: 3                 # 유지할 Pod 개수
  selector:
    matchLabels:
      type: frontend           # ⚠️ 아래 template.metadata.labels와 반드시 "정확히" 일치해야 함
  template:                     # 새로 만들 Pod의 틀
    metadata:
      labels:
        type: frontend           # ⚠️ 위 selector.matchLabels와 일치
    spec:
      containers:
        - name: nginx-container
          image: nginx
```

**자주 나는 에러 3가지**

| 증상 | 원인 |
|---|---|
| `no matches for kind "ReplicaSet" in version "v1"` | `apiVersion: v1`로 잘못 씀 → `apps/v1`로 수정 |
| `spec.template.metadata.labels: Invalid value: ... selector does not match template labels` | `selector.matchLabels`와 `template.metadata.labels`가 서로 다름 → 두 곳의 키·값을 정확히 똑같이 맞추기 |
| `kubectl delete <이름>` → `the server doesn't have a resource type "<이름>"` | 타입을 안 쓰고 이름만 씀 → `kubectl delete replicaset <이름>`처럼 타입+이름 둘 다 필요 |

**참고**: `kubectl create deployment`처럼 `kubectl create replicaset`이라는 명령형 단축 명령은 **없다**. YAML 뼈대가 필요하면 Deployment로 생성한 뒤 수정하는 트릭을 쓴다.

```bash
kubectl create deployment temp --image=nginx --replicas=3 --dry-run=client -o yaml > rs.yaml
# 그 다음 rs.yaml에서: kind: Deployment → ReplicaSet 로 수정, strategy: 블록 삭제

# 또는 필드 구조가 헷갈릴 때 바로 문서 확인
kubectl explain replicaset --recursive
kubectl explain replicaset.spec.selector
```

## 🦐 selector = 동적 그룹화(Dynamic Grouping)

selector의 본질은 "이름으로 콕 집어 관리"가 아니라, **라벨 조건에 맞는 Pod를 전부 동적으로 찾아서** 관리 대상으로 삼는 것이다. Pod가 몇 개든(10개든 10만 개든) 같은 라벨만 붙어 있으면 하나의 selector로 전부 커버된다.

- **ReplicaSet의 selector**: 이 라벨을 가진 Pod가 지금 몇 개인지 계속 세면서, `replicas`(desired count)와 맞을 때까지 만들거나 지운다. 개별 Pod의 CPU/메모리 같은 상태를 들여다보는 게 아니라 **존재 개수**만 관리한다는 점에 주의.
- **Service의 selector**: 이 라벨을 가진 Pod들이 어디 있는지 찾아서 트래픽을 보낼 대상 목록([[05-서비스와_네트워킹|Endpoints]])을 만든다.

그래서 여러 컨트롤러/Service가 각자 다른(또는 겹치는) selector로 같은 Pod 집합을 서로 다른 목적으로 동시에 바라볼 수 있다.

> ⚠️ **Adoption 함정**: ReplicaSet이 관리하는 라벨과 똑같은 라벨을 가진 Pod를 **수동으로 하나 더 만들면**, ReplicaSet은 그 Pod도 "내 자식"으로 인식(adopt)해버린다. 그러면 실제 개수가 desired보다 하나 더 많아지므로, ReplicaSet이 초과분 중 아무거나 하나를 골라 삭제할 수 있다 — 위에서 언급한 "아무 Pod나 종료된다" 현상의 근본 원인이 바로 이것.

## 🦐 ReplicaSet vs ReplicationController

정확한 명칭은 `ReplicationController`(RC)예요 — ReplicaSet(RS)의 **전신(구버전)** 오브젝트입니다. 하는 일(지정된 수의 Pod 유지, self-healing)은 동일하지만 몇 가지 차이가 있어요.

| | **ReplicationController** (구) | **ReplicaSet** (신, 현재 표준) |
|---|---|---|
| API 버전 | `v1` | `apps/v1` |
| 셀렉터 방식 | **동등 기반(equality-based)만 지원** — `key: value` 형태로 정확히 일치하는 것만 | **집합 기반(set-based)까지 지원** — `matchLabels` + `matchExpressions`(`In`, `NotIn`, `Exists` 등)로 더 유연한 조건 가능 |
| Deployment와의 관계 | Deployment가 관리하지 **않음** (Deployment는 항상 ReplicaSet을 만듦) | Deployment가 내부적으로 자동 생성·관리 |
| 현재 상태 | 사실상 레거시. 새로 만들 이유가 없음 | 표준. 다만 이마저도 보통 Deployment를 통해 간접적으로만 다룸 |

```yaml
# ReplicaSet의 set-based selector 예시 (RC로는 불가능)
selector:
  matchExpressions:
    - {key: tier, operator: In, values: [frontend, backend]}
```

**결론**: RC는 하위 호환을 위해 API에 남아있을 뿐, 실무/시험 어디서도 새로 만들 이유가 없다. "RS는 RC의 상위 호환이고, RC는 이제 안 쓴다"고만 기억하면 충분하다.

## 🦐 Deployment — 선언적 업데이트 + 롤백

- ReplicaSet을 감싸는 상위 컨트롤러. **Pod 이미지/스펙을 바꿀 때 무중단으로 점진적 교체(Rolling Update)** 하고, 문제가 생기면 **이전 버전으로 롤백**할 수 있게 해준다.
- Deployment의 스펙을 바꾸면(예: 이미지 태그 변경) 새 ReplicaSet이 하나 더 생성되고, 기존 ReplicaSet의 Pod 수를 서서히 줄이면서 새 ReplicaSet의 Pod 수를 서서히 늘린다. 이전 ReplicaSet들은 0개로 줄어든 채 **revision history**로 남아 롤백에 쓰인다.
- 배포 전략(`spec.strategy.type`): `RollingUpdate`(기본, 무중단) vs `Recreate`(기존 Pod 전부 종료 후 새로 생성, 다운타임 있음).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # 업데이트 중 동시에 내려갈 수 있는 최대 Pod 수
      maxSurge: 1          # 업데이트 중 초과로 띄울 수 있는 최대 Pod 수
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

### Deployment 관련 명령어

```bash
kubectl create deployment nginx-deploy --image=nginx:1.27 --replicas=3   # 명령형 생성
kubectl apply -f deployment.yaml                                          # 선언형 생성/갱신

kubectl get deployments
kubectl get rs                          # Deployment가 만든 ReplicaSet도 함께 확인
kubectl rollout status deployment/nginx-deploy    # 롤아웃 진행 상황 실시간 확인

# 이미지 업데이트 (롤링 업데이트 트리거)
kubectl set image deployment/nginx-deploy nginx=nginx:1.28

# 스케일
kubectl scale deployment/nginx-deploy --replicas=5

# 롤백
kubectl rollout history deployment/nginx-deploy         # 리비전 목록
kubectl rollout undo deployment/nginx-deploy             # 바로 이전 버전으로
kubectl rollout undo deployment/nginx-deploy --to-revision=2   # 특정 리비전으로

# 일시정지/재개 (여러 변경을 한 번에 롤아웃하고 싶을 때)
kubectl rollout pause deployment/nginx-deploy
kubectl rollout resume deployment/nginx-deploy
```

## 🦐 배포 전략 (예정 학습) — CKAD 핵심 출제 영역

Kubernetes에 "블루/그린"이나 "카나리"라는 전용 오브젝트는 없다 — **여러 Deployment/Service 조합으로 직접 구현**하는 방식이 시험 포인트다.

- **Rolling Update**: 위에서 다룬 Deployment 기본 전략. 점진적 교체.
- **Recreate**: 구버전 전체 종료 후 신버전 전체 생성. 다운타임 있지만 구버전/신버전 동시 존재를 피해야 할 때 사용.
- **Blue/Green**: 신버전(Green)을 별도 Deployment로 완전히 띄운 뒤, Service의 `selector`(라벨)만 한 번에 Blue → Green으로 전환. 즉시 전환/즉시 롤백 가능하지만 리소스 2배 필요.
- **Canary**: 신버전을 소수의 Pod만 띄워(예: 기존 9개 + 신버전 1개), 같은 Service selector 아래 두어 트래픽 일부만 새 버전으로 흘려보내며 검증. 라벨은 공유하되 버전 라벨만 다르게 둬서 구현.

## 🦐 `kubectl create` vs `kubectl apply`

둘 다 리소스를 "만드는" 데 쓰지만, **이미 존재하는 리소스에 다시 실행했을 때 어떻게 되느냐**가 결정적 차이다.

| | `kubectl create -f file.yaml` | `kubectl apply -f file.yaml` |
|---|---|---|
| 리소스가 없을 때 | 생성 | 생성 |
| 리소스가 이미 있을 때 | **에러** (`AlreadyExists`) | 달라진 필드만 **patch**(업데이트) |
| 여러 번 실행 | 두 번째부터 에러 | 몇 번을 실행해도 안전 (멱등성, idempotent) |
| 방식 | 명령형(imperative) — "지금 이 내용으로 딱 한 번 만들어라" | 선언형(declarative) — "클러스터가 이 YAML과 같은 상태가 되도록 유지해라" |

`apply`는 리소스에 `kubectl.kubernetes.io/last-applied-configuration` 어노테이션을 저장해두고, 다음 `apply` 때 "마지막 적용값 vs 실제 클러스터 상태 vs 새 YAML" 셋을 비교(3-way merge)해서 정확히 뭐가 바뀌었는지 계산한다. YAML 파일을 계속 고쳐가며 재적용하는 실무/GitOps 환경에서는 거의 항상 `apply`를 쓰고, `create`는 "절대 이미 존재하면 안 된다"를 보장하고 싶을 때나 1회성 생성에만 쓴다.

## 🦐 Helm / Kustomize (예정 학습)

- **Helm**: 쿠버네티스용 패키지 매니저. "Chart"라는 템플릿 묶음으로 애플리케이션을 배포/버전 관리. `helm install`, `helm upgrade`, `helm rollback` 등.
- **Kustomize**: 템플릿 엔진 없이 base YAML + overlay(패치)로 환경별 설정 차이를 관리. `kubectl apply -k` 로 바로 사용 가능 (kubectl에 내장).
