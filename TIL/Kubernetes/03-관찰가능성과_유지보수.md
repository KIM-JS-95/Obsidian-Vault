## 🦐 헬스체크(Probe)

컨테이너가 "떠 있다(Running)"는 것과 "정상 동작한다"는 것은 다르다. 이를 구분하기 위한 3가지 프로브:

| Probe | 실패 시 동작 | 용도 |
|---|---|---|
| `livenessProbe` | **컨테이너를 재시작** | 데드락 등으로 응답 불가 상태에 빠진 컨테이너 감지 |
| `readinessProbe` | Pod를 **Service의 Endpoints에서 제외** (컨테이너 재시작 X) | 아직 트래픽 받을 준비가 안 된 Pod로 요청이 가지 않도록 차단 — [[05-서비스와_네트워킹]]의 Endpoints와 바로 연결되는 개념 |
| `startupProbe` | 계속 실패하면 컨테이너를 재시작 | 시작이 느린 애플리케이션에게 초기 구동 시간을 벌어줌 (성공 전까지 liveness/readiness는 대기) |

```yaml
    livenessProbe:
      httpGet:
        path: /healthz
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 80
      periodSeconds: 5
```

프로브 방식은 `httpGet` 외에도 `exec`(커맨드 실행 성공/실패로 판단), `tcpSocket`(포트 연결 성공 여부)도 있다.

```yaml
    livenessProbe:
      exec:
        command: ["cat", "/tmp/healthy"]
    readinessProbe:
      tcpSocket:
        port: 3306
```

## 🦐 컨테이너 로그 & 디버깅 명령어

```bash
# 로그
kubectl logs nginx-pod                                    # 컨테이너 로그
kubectl logs nginx-pod -c <container> --previous            # 멀티 컨테이너 Pod / 재시작 전(크래시 직전) 로그
kubectl logs -f nginx-pod                                   # 실시간 tail
kubectl logs -l app=nginx --all-containers                   # 라벨로 여러 Pod 로그 한 번에

# 접속/디버깅
kubectl exec -it nginx-pod -- /bin/sh                        # 컨테이너 쉘 접속
kubectl exec nginx-pod -- env                                 # 쉘 없이 단발성 명령 실행
kubectl port-forward pod/nginx-pod 8080:80                    # 로컬 8080 → Pod 80 포트 포워딩 (임시 접속 테스트)
kubectl cp nginx-pod:/var/log/app.log ./app.log                # 파일 복사
kubectl top pod                                                 # CPU/메모리 사용량 (metrics-server 필요)
kubectl describe pod nginx-pod                                    # 상세 정보 + Events (문제 진단 시 최우선 확인)
kubectl get events --sort-by=.lastTimestamp                        # 네임스페이스 전체 이벤트 시간순 확인

# 임시 디버깅용 컨테이너 추가 (Pod 정의를 바꾸지 않고 붙여서 조사)
kubectl debug nginx-pod -it --image=busybox --target=nginx
```

> 문제가 생긴 Pod를 볼 때는 항상 이 순서로: ① `kubectl get pods` (상태 확인) → ② `kubectl describe pod <name>` (Events 확인) → ③ `kubectl logs <name>` (애플리케이션 자체 로그 확인).

## 🦐 CrashLoopBackOff

컨테이너가 시작된 직후 **반복적으로 죽고 있다**는 뜻의 Pod 상태.

- **CrashLoop**: 시작 → 죽음(exit) → `restartPolicy`에 따라 kubelet이 재시작 → 또 죽음... 의 반복
- **BackOff**: 재시작 시도 간격을 매번 지수적으로 늘리는 것 (10초 → 20초 → 40초 → ... 최대 5분). 즉시 계속 재시작해봐야 소용없으니 쿠버네티스가 스스로 텀을 둠

주로 `restartPolicy: Always`(Deployment/ReplicaSet 기본값)에서 마주친다.

**흔한 원인**
- 애플리케이션 코드/설정 에러로 시작하자마자 예외 발생 후 종료
- 필요한 환경변수/설정파일이 없어서 초기화 실패
- Dockerfile의 `CMD`/`ENTRYPOINT`가 잘못돼서 즉시 종료되는 명령을 실행
- 연결해야 할 DB 등 의존 서비스가 아직 준비 안 돼서 앱이 죽어버림 (→ `initContainers`로 대기시키는 게 정석 해법, [[01-애플리케이션_설계와_빌드]] 참고)
- 메모리 제한(`limits.memory`) 초과로 `OOMKilled` 반복

**진단 순서**
```bash
kubectl get pods                                # RESTARTS 열 숫자가 계속 올라가는지 확인
kubectl describe pod <이름>                       # Events 섹션 + Last State의 Reason(OOMKilled 등) 확인
kubectl logs <이름>                                # 현재(재시작된 뒤) 로그 — 비어있을 수도 있음
kubectl logs <이름> --previous                       # ⭐ 핵심: 죽기 직전(이전 인스턴스)의 로그 — 진짜 에러는 보통 여기 있음
```

> ⚠️ `kubectl logs`만 보고 "로그가 비어있네?"라고 헷갈리기 쉽다. 방금 재시작된 컨테이너는 아직 로그가 없을 수 있으므로, 반드시 `--previous`도 같이 확인할 것.

1. `readinessProbe`만 실패하고 `livenessProbe`는 통과하는 Pod가 있다면, 이 Pod는 `kubectl get pods`에서 `Running`으로 보일까 아닐까? 그리고 Service는 이 Pod로 트래픽을 보낼까?
2. `kubectl logs`로 아무것도 안 나오는데 `kubectl describe pod`의 Events에는 `CrashLoopBackOff`가 보인다면, 뭘 먼저 확인해야 할까? (힌트: `--previous`)
