## 🦐 Pod — 최소 배포 단위

- 쿠버네티스에서 스케줄링되는 가장 작은 단위. 하나 이상의 컨테이너를 감싸며, 그 안의 컨테이너들은 **같은 네트워크 네임스페이스(같은 IP, `localhost`로 서로 통신)** 와 **같은 볼륨**을 공유한다.
- 컨테이너 1개 = Pod 1개가 가장 흔한 형태지만, 로깅/프록시 등을 붙이는 사이드카(sidecar) 패턴처럼 여러 컨테이너를 한 Pod에 묶기도 한다. **CKAD는 이 멀티 컨테이너 설계를 직접 출제 범위로 명시**하고 있어 특히 중요.
- Pod는 기본적으로 **일회성(ephemeral)** 이다. Pod를 단독으로 만들면 노드 장애나 삭제 시 다시 만들어지지 않는다 — 그래서 실무에서는 거의 항상 컨트롤러(ReplicaSet/Deployment)를 통해 생성한다.

```yaml
# pod.yaml — 최소 예시
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
```

## 🦐 Pod 라이프사이클

Pod가 만들어져서 없어지기까지 거치는 단계(`status.phase`)는 5가지다.

| Phase | 의미 |
|---|---|
| `Pending` | API 서버에는 생성됐지만, 아직 노드에 스케줄되지 않았거나 이미지 다운로드 등 준비 중 |
| `Running` | 노드에 배정 완료, 컨테이너 1개 이상이 실행 중(또는 시작/재시작 중) |
| `Succeeded` | 모든 컨테이너가 정상 종료(exit 0)되고 재시작되지 않음 — 주로 Job에서 나타남 |
| `Failed` | 모든 컨테이너가 종료됐고, 그중 하나 이상이 실패(non-zero exit) |
| `Unknown` | kubelet과 통신이 끊겨 상태를 알 수 없음 (노드 장애 등) |

Pod 내부 각 컨테이너의 상태(`status.containerStatuses[].state`)는 별도로 3가지: `Waiting`(이미지 pull 등 시작 전) / `Running`(정상 실행 중) / `Terminated`(종료됨, exit code 포함).

**restartPolicy** (Pod 전체에 적용되는 재시작 정책, 컨테이너가 죽었을 때 kubelet이 취하는 동작):

| 값 | 동작 | 주 사용처 |
|---|---|---|
| `Always` (기본값) | 항상 재시작 | Deployment/ReplicaSet — 이 값이 아니면 애초에 생성 불가 |
| `OnFailure` | 비정상 종료(exit ≠ 0)일 때만 재시작 | **Job** (배치 작업) — CKAD에서 Job/CronJob과 묶어서 자주 나옴 |
| `Never` | 재시작 안 함 | 1회성 진단용 Pod 등 |

> ⚠️ Deployment/ReplicaSet으로 만든 Pod는 `restartPolicy: Always`만 허용된다. "Pod가 계속 재시작된다"는 문제 상황이 나오면 restartPolicy가 아니라 컨테이너 자체가 크래시하고 있다는 신호로 봐야 한다 (`CrashLoopBackOff`).

## 🦐 Init Container

메인(app) 컨테이너가 시작되기 **전에 순서대로** 실행되고 완료(exit 0)되어야 다음으로 넘어가는 컨테이너. 설정 파일 미리 받아오기, DB 준비될 때까지 대기하기 같은 초기화 작업에 쓴다. 실패하면 정책에 따라 재시도되며, 메인 컨테이너는 그동안 시작되지 않는다.

```yaml
  initContainers:
    - name: wait-for-db
      image: busybox
      command: ['sh', '-c', 'until nslookup db-svc; do sleep 2; done']
```

## 🦐 멀티 컨테이너 Pod 디자인 패턴 (CKAD 핵심 출제 영역)

![멀티 컨테이너 Pod — 파일을 받아오는 사이드카와 웹서버가 emptyDir 볼륨을 공유하는 예시](https://kubernetes.io/images/docs/pod.svg)
*(출처: 공식 문서 — 사이드카 컨테이너가 파일을 받아오고, 웹서버 컨테이너가 그 파일을 서빙. 두 컨테이너가 emptyDir 볼륨을 공유)*

같은 Pod 안에 여러 컨테이너를 두는 이유와 대표 패턴 세 가지.

| 패턴 | 설명 | 예시 |
|---|---|---|
| **Sidecar** | 메인 컨테이너를 보조하는 컨테이너를 나란히(sidecar) 배치. 메인 컨테이너와 동시에 계속 실행됨 | 로그 수집기, 프록시(예: 서비스 메시의 Envoy) |
| **Ambassador** | 메인 컨테이너의 네트워크 요청을 대신 받아 외부로 중계/프록시하는 컨테이너 | 외부 DB 연결을 단순화해주는 프록시 |
| **Adapter** | 메인 컨테이너가 만든 출력(로그 등)을 표준화된 형식으로 변환해서 내보내는 컨테이너 | 로그 포맷을 모니터링 시스템이 이해하는 형식으로 변환 |

Init Container도 넓게 보면 이 "멀티 컨테이너 설계"의 일부(순차 실행 vs sidecar의 동시 실행 차이로 구분).

> 💡 **Structural Pattern vs Behavioral Pattern**: 여기서 다룬 Sidecar/Ambassador/Adapter/Init Container는 "**한 Pod 안에서** 컨테이너를 어떻게 조합하느냐"를 다루는 **Structural Pattern**이다. 이와 별개로 "**여러 Pod 복제본 중 하나만** 특정 작업을 수행하게 만드는" 문제(예: `@Scheduled` 배치 작업의 중복 실행 방지)는 **Behavioral Pattern**(Singleton Service, Periodic Job 등)으로 분류되는 다른 카테고리다 — [[../Spring/디자인패턴/싱글톤_서비스_패턴(K8s)|실무 적용 사례(ShedLock)는 여기 정리]].

## 🦐 종료(Graceful Shutdown) 이론

Pod를 삭제하면 즉시 죽는 게 아니라: kubelet이 컨테이너에 **SIGTERM**을 보내고 → `terminationGracePeriodSeconds`(기본 30초) 만큼 대기 → 그래도 안 죽으면 **SIGKILL**로 강제 종료. 이 사이에 readinessProbe가 실패로 전환되며 Service Endpoints에서도 먼저 빠진다. (애플리케이션이 SIGTERM을 무시하도록 짜여 있으면 항상 30초 뒤에야 종료되는 문제로 이어짐.)

## 🦐 Job / CronJob (예정 학습)

- **Job**: 한 번 실행하고 끝나면 되는 배치 작업용 컨트롤러. `restartPolicy: OnFailure` 또는 `Never`와 함께 사용. `completions`, `parallelism`으로 몇 번/몇 개 동시에 실행할지 지정.
- **CronJob**: Job을 cron 스케줄(`schedule: "*/5 * * * *"`)에 따라 주기적으로 생성해주는 상위 컨트롤러.
- 다음 세션에서 YAML 예시와 명령어(`kubectl create job`, `kubectl create cronjob` 등) 추가 예정.

## 🦐 볼륨 (예정 학습)

- **Ephemeral volume** (`emptyDir` 등): Pod 생존 기간 동안만 유지되는 임시 저장소. 같은 Pod 안의 여러 컨테이너가 파일을 공유할 때 자주 씀.
- **Persistent volume** (PV/PVC): Pod가 사라져도 데이터가 남아야 할 때 사용. 스토리지 도메인과 겹치는 영역이라 추후 별도 정리 예정.

### Pod 관련 명령어

```bash
# 생성/조회
kubectl run nginx-pod --image=nginx:1.27 --port=80    # 명령형으로 Pod 즉석 생성
kubectl apply -f pod.yaml                              # 선언형으로 생성/갱신
kubectl get pods                                        # Pod 목록
kubectl get pods -o wide                                 # 노드/IP까지 표시
kubectl get pod nginx-pod -o yaml                         # 전체 스펙/상태를 YAML로 확인
kubectl get pod nginx-pod -o jsonpath='{.status.phase}'    # 특정 필드만 추출 (스크립팅용)
kubectl describe pod nginx-pod                           # 상세 정보 + 이벤트

# 수정/삭제
kubectl label pod nginx-pod tier=frontend                        # 라벨 추가/변경
kubectl annotate pod nginx-pod owner=jsung                        # 어노테이션 추가
kubectl edit pod nginx-pod                                          # 즉석 수정 (일부 필드는 재생성 없이 변경 불가)
kubectl delete pod nginx-pod                                         # 삭제 (그레이스풀, 기본 30초 대기)
kubectl delete pod nginx-pod --grace-period=0 --force                 # 강제 즉시 삭제 (디버깅 시에만 권장)
```

> 로그 확인, `exec`, `port-forward` 등 관찰/디버깅용 명령어는 [[03-관찰가능성과_유지보수]] 노트로 옮겨서 정리했습니다.
