## 🦐 Service가 필요한 이유

Pod는 죽었다 다시 뜰 때마다 **IP가 바뀐다**. Deployment가 Pod를 교체할 때마다 클라이언트가 매번 새 IP를 알아내야 한다면 쓸 수가 없다.

**Service**는 label selector로 대상 Pod 그룹을 찾아, 그 앞단에 **고정된 가상 IP(ClusterIP)와 DNS 이름**을 부여해주는 오브젝트다. 실제 트래픽 라우팅(로드밸런싱)은 각 노드에서 실행 중인 **`kube-proxy`** 가 iptables(또는 IPVS) 규칙으로 처리한다.

```
Client ──▶ Service (고정 IP/DNS, 예: nginx-svc)
                │  selector: app=nginx 로 대상 Pod 탐색
                ▼
        Pod A   Pod B   Pod C   (IP는 계속 바뀌어도 됨)
```

Service가 관리하는 대상 Pod 목록은 **Endpoints(또는 EndpointSlice)** 오브젝트에 자동으로 채워진다 — 트러블슈팅 시 `kubectl get endpoints`로 "Service가 실제로 어떤 Pod를 보고 있는지" 확인하는 게 핵심 체크포인트.

## 🦐 Service 타입 4가지

| 타입 | 접근 범위 | 설명 |
|---|---|---|
| `ClusterIP` (기본값) | 클러스터 내부 전용 | 클러스터 내부 DNS(`<svc-name>.<namespace>.svc.cluster.local`)로만 접근 가능. 마이크로서비스 간 내부 통신에 사용. |
| `NodePort` | 클러스터 외부 (노드 IP + 포트) | 모든 노드의 동일한 포트(기본 범위 30000-32767)를 열어 외부에서 `<노드IP>:<NodePort>`로 접근. 내부적으로 ClusterIP도 함께 생성됨. |
| `LoadBalancer` | 클러스터 외부 (클라우드 LB) | 클라우드 제공자(AWS/GCP 등)에 외부 로드밸런서를 자동 프로비저닝. 온프레미스에서는 MetalLB 같은 별도 컨트롤러가 없으면 `<pending>` 상태로 남음. NodePort/ClusterIP를 감싸는 상위 타입. |
| `ExternalName` | - | Pod selector 없이, 클러스터 내부에서 특정 외부 도메인으로 가는 DNS CNAME 별칭만 만들어줌 (예: 외부 DB 주소를 내부 이름으로 참조). |

### 🦐 ClusterIP / NodePort / LoadBalancer는 서로 감싸는 관계

세 타입을 각각 별개로 외우기보다, **포함 관계**로 이해하면 훨씬 쉽다.

```
LoadBalancer   ─(클라우드 외부 로드밸런서, 고정 공인 IP)
     └─ 내부적으로 NodePort를 자동 생성
              NodePort   ─(모든 노드에 똑같이 뚫린 외부 진입 포트)
                   └─ 내부적으로 ClusterIP를 자동 생성
                            ClusterIP   ─(클러스터 내부 전용 가상 IP)
                                 └─ selector로 찾은 Pod들
```

**ClusterIP** — 세 타입 중 가장 기본. 클러스터 **내부에서만** 도달 가능한 고정 가상 IP + DNS 이름. 외부에서는 절대 못 들어온다. 주 용도: 마이크로서비스 간 내부 통신 (예: frontend Pod가 backend Pod를 호출, backend Pod가 DB Pod를 호출).

**NodePort** — ClusterIP 기능을 그대로 포함하면서, 추가로 **모든 노드에 똑같은 포트(예: 30080)를 열어** 외부에서 `<아무 노드 IP>:30080`으로 들어올 수 있게 해준다. 구체적인 3-포트 흐름은 아래 예시로.

**LoadBalancer** — NodePort 기능까지 그대로 포함하면서, 그 위에 **클라우드 제공자의 실제 외부 로드밸런서**(AWS ELB, GCP LB 등, 고정 공인 IP 부여)를 자동으로 하나 만들어 붙여준다. 그 로드밸런서가 각 노드의 NodePort로 트래픽을 분산해주는 구조. 그래서 `kubectl get svc`로 LoadBalancer 타입을 보면 `NodePort`처럼 30000번대 포트도 같이 할당된 걸 볼 수 있다. 온프레미스(자체 서버) 환경에는 이 자동 프로비저닝 기능이 없어서, MetalLB 같은 별도 컨트롤러를 설치하지 않으면 `EXTERNAL-IP`가 계속 `<pending>`으로 남는다.

### 🦐 NodePort 3-포트 흐름 예시 (숫자로 따라가기)

```yaml
spec:
  type: NodePort
  ports:
    - port: 80          # ① Service의 ClusterIP 쪽 포트 — "내선번호"
      targetPort: 80      # ② 컨테이너 안의 실제 포트 — "사무실 안 내 자리"
      nodePort: 30080      # ③ 모든 노드에 뚫린 외부 진입 포트 — "건물 정문 외부 직통번호"
```

```
내 브라우저 → http://<아무 노드 IP>:30080   (③ nodePort, 외부 진입점)
                    ↓ 그 노드의 kube-proxy가 받아서
              ClusterIP:80                  (① port, 내부 대표 주소)
                    ↓ selector로 Pod 하나 선택
              Pod의 80번                     (② targetPort, 실제 컨테이너)
```

> 💡 핵심 포인트: `nodePort`는 **Pod가 실제로 떠 있지 않은 노드**로 접속해도 정상 동작한다. 모든 노드의 kube-proxy가 "나한텐 없어도 어디 있는지는 안다"는 식으로 트래픽을 넘겨주기 때문에, 클러스터의 아무 노드 IP나 진입점으로 쓸 수 있다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  type: ClusterIP        # NodePort / LoadBalancer / ExternalName 도 가능
  selector:
    app: nginx            # 이 라벨을 가진 Pod들을 대상으로 삼음
  ports:
    - port: 80             # Service 자체의 포트
      targetPort: 80        # 실제 Pod(container)의 포트
      # nodePort: 30080     # type: NodePort일 때만 지정 가능 (생략 시 자동 할당)
```

### Service 관련 명령어

```bash
kubectl expose deployment nginx-deploy --port=80 --target-port=80 --type=ClusterIP   # 명령형 생성
kubectl apply -f service.yaml                                                          # 선언형 생성/갱신

kubectl get svc                        # Service 목록 (CLUSTER-IP, PORT(S) 확인)
kubectl describe svc nginx-svc         # selector, endpoint 등 상세
kubectl get endpoints nginx-svc         # 실제 연결된 Pod IP:PORT 목록 (⭐ 트러블슈팅 1순위)

# 임시로 클러스터 내부에서 접속 테스트 (디버깅용 Pod)
kubectl run tmp-shell --rm -it --image=busybox -- sh
# 컨테이너 안에서: wget -O- nginx-svc:80
```

> ⚠️ 실전에서 가장 흔한 실수: Service의 `selector`가 Pod의 `labels`와 **한 글자라도** 다르면 (`app: nginx` vs `app: Nginx` 등) `kubectl get endpoints`가 빈 값으로 나온다. Service가 "연결이 안 될 때"는 항상 라벨 일치 여부부터 확인.

### ⭐ CKAD 실전 팁 — `kubectl expose` vs `kubectl create service`

Service를 imperative 명령으로 빠르게 뽑아낼 수 있는 방법이 두 가지 있는데, 동작 방식이 미묘하게 달라서 상황에 맞게 골라야 한다. ([[02-애플리케이션_배포|Imperative 3가지 방식]] 참고 — 이것도 결국 ①번 imperative command로 뼈대를 뽑고 다듬는 패턴)

**`kubectl expose`** — 대상 Pod/Deployment의 라벨을 **자동으로 읽어서 selector로 그대로 채워준다.** 그래서 실제로 그 Pod에 연결되는 Service를 정확하게 만든다.

```bash
kubectl expose pod redis --port=6379 --name=redis-service --dry-run=client -o yaml
```

단점: NodePort 타입으로 만들 때 **nodePort 번호를 직접 지정하는 옵션이 없다.** 특정 포트(예: 30080)가 꼭 필요하면, YAML을 뽑은 뒤 `nodePort` 필드를 손으로 추가해야 한다.

```bash
kubectl expose pod nginx --type=NodePort --port=80 --name=nginx-service --dry-run=client -o yaml
# → 출력된 YAML에서 nodePort: 30080 줄을 직접 추가한 뒤 apply
```

**`kubectl create service`** — 반대로 selector를 Pod의 실제 라벨에서 읽어오지 않고, 그냥 `app=<이름>`으로 **임의로** 채운다. Pod의 라벨이 우연히 `app=redis`면 맞아떨어지지만, 라벨이 다르면(`role: cache` 등) 이 selector는 실제로 아무 Pod도 못 찾는다 — selector를 직접 지정하는 옵션도 없어서 YAML을 뽑은 뒤 손으로 고쳐야 한다. 대신 **`--node-port`로 원하는 포트 번호를 바로 지정**할 수 있다는 게 `expose`와 정반대되는 장점.

```bash
kubectl create service clusterip redis --tcp=6379:6379 --dry-run=client -o yaml
kubectl create service nodeport nginx --tcp=80:80 --node-port=30080 --dry-run=client -o yaml
```

| | `kubectl expose` | `kubectl create service` |
|---|---|---|
| selector | Pod의 실제 라벨을 자동으로 읽음 (정확) | `app=<이름>`으로 임의 지정 (틀릴 수 있음) |
| NodePort 번호 지정 | ❌ 불가 (YAML 생성 후 수동 추가 필요) | ✅ `--node-port`로 바로 지정 가능 |

> 💡 실전 권장: **기본은 `kubectl expose`를 쓰고**, 특정 NodePort 번호가 꼭 필요하면 `--dry-run=client -o yaml`로 뽑은 다음 `nodePort` 필드만 손으로 추가해서 적용한다. `kubectl create service`는 selector가 우연히 맞아떨어지는 상황이 아니면 잘 안 쓰는 게 안전하다.

## 🦐 Ingress (예정 학습)

Service(특히 LoadBalancer)는 서비스 하나당 외부 접점 하나가 필요해서 서비스가 많아지면 비효율적이다. **Ingress**는 L7(HTTP/HTTPS) 레벨에서 도메인/경로 기준으로 여러 Service에 트래픽을 라우팅해주는 오브젝트 — 예: `example.com/api` → api-svc, `example.com/web` → web-svc. Ingress 리소스 자체는 "규칙"만 정의하고, 실제 동작은 **Ingress Controller**(nginx-ingress 등)가 수행한다는 점이 핵심.

![Ingress — 외부 클라이언트가 하나의 진입점을 통해 경로 기준으로 여러 Service에 라우팅되는 구조](https://kubernetes.io/docs/images/ingress.svg)
*(출처: 공식 문서 — 하나의 Ingress가 여러 Service를 대상으로 트래픽을 분배)*

**경로 기반 라우팅(Fan Out)** 예시 — 하나의 도메인 아래 경로별로 다른 Service로 분기:

![Ingress Fan Out — 같은 도메인의 서로 다른 경로를 서로 다른 Service로 라우팅](https://kubernetes.io/docs/images/ingressFanOut.svg)

## 🦐 NetworkPolicy (예정 학습)

기본적으로 쿠버네티스는 **모든 Pod가 서로 자유롭게 통신 가능**하다. NetworkPolicy는 라벨 기준으로 "이 Pod는 이런 트래픽만 받거나 보낼 수 있다"는 방화벽 규칙을 정의한다. CNI 플러그인이 NetworkPolicy를 지원해야 실제로 동작(Flannel은 미지원, Calico/Cilium 등은 지원).

2. `kubectl get svc`에는 Service가 정상으로 보이는데 `kubectl get endpoints`가 비어 있다면, 가장 먼저 의심해야 할 원인은?
