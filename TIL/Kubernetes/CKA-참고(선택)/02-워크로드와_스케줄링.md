## 🦐 kube-scheduler — Pod를 Node에 "배정"만 하는 두뇌

[[00a-핵심_컴포넌트_복습노트|핵심 컴포넌트 복습노트]]에서 다뤘듯, kube-scheduler는 컨트롤 플레인 소속이고 **배정만 하지 실행은 하지 않는다.** 새로 생성됐지만 아직 `spec.nodeName`이 비어있는(=어느 Node에서 뜰지 정해지지 않은) Pod를 찾아서, 가장 적합한 Node 하나를 골라 그 필드를 채워주는 게 전부다. 실제로 컨테이너를 띄우는 건 그 Node의 kubelet 몫.

### 동작 흐름 — Watch → Filtering → Scoring → Bind

```
새 Pod 생성 (spec.nodeName: 비어있음)
        │
        ▼
kube-scheduler가 감지 (API 서버를 Watch)
        │
        ▼
① Filtering (예선) — 이 Pod를 절대 실행할 수 없는 Node를 제외
   예: 자원 부족(CPU/메모리) · taint를 tolerate 못함 · nodeSelector 불일치 등
        │
        ▼  실행 가능한 Node 목록(feasible nodes)만 남음
② Scoring (본선) — 남은 Node들에 점수(0~10)를 매겨 순위 결정
   예: 자원이 더 여유로운 Node 우대 · nodeAffinity 선호조건 만족 여부 등
        │
        ▼  최고 점수 Node 확정
③ Bind — API 서버에 배정 기록 (Pod의 spec.nodeName이 채워짐)
        │
        ▼
④ 그 Node의 kubelet이 넘겨받아 실제 컨테이너 실행
```

핵심은 **①에서 "가능/불가능"을 걸러내고, ②에서 남은 후보들 중 "가장 나은" 곳을 고른다**는 2단계 구조라는 것 — 자격 미달(Filtering)과 우선순위(Scoring)를 분리해서 생각하면 헷갈리지 않는다.

> 💡 참고로 최신 kube-scheduler는 내부적으로 PreFilter/Filter/PreScore/Score/Reserve/Permit/Bind 같은 더 세분화된 플러그인 확장점("Scheduling Framework")으로 동작하지만, CKA/CKAD 레벨에서는 위의 **Filtering → Scoring → Bind** 3단계 멘탈 모델이면 충분하다.

### 🦐 배정 가능한 Node가 하나도 없다면?

Pod는 [[../01-애플리케이션_설계와_빌드|Pod 라이프사이클]]에서 다룬 그 `Pending` 상태로 남는다. `kubectl describe pod`로 확인하면 Events에 정확한 사유가 나온다.

```
Events:
  Warning  FailedScheduling  ...  0/3 nodes are available: 3 Insufficient cpu.
```

"Pod가 `Pending`에서 안 넘어가요"라는 문제의 흔한 원인 순서: **① Node 자원 부족 → ② taint를 tolerate 안 함 → ③ nodeSelector/nodeAffinity 불일치.** 이 순서대로 `describe`의 Events를 읽으면 원인이 바로 보인다.

### 🦐 수동 스케줄링 — kube-scheduler를 통째로 건너뛰기

kube-scheduler는 `spec.nodeName`이 **비어있는** Pod만 감시 대상으로 삼는다. 반대로 말하면, Pod YAML을 작성할 때 처음부터 `spec.nodeName`을 직접 채워두면 kube-scheduler는 이 Pod의 존재 자체를 무시하고, 지정된 Node의 kubelet이 곧바로 컨테이너를 실행해버린다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: manual-pod
spec:
  nodeName: node01     # ⚠️ 스케줄러를 완전히 우회 — Filtering/Scoring 자체가 아예 작동하지 않음
  containers:
    - name: nginx
      image: nginx
```

> ⚠️ 이미 생성된 Pod의 `nodeName`은 **수정 불가(immutable)** 다. "이미 만든 Pod를 다른 Node로 옮기고 싶다"면 무조건 삭제 후 재생성해야 한다.

### 🦐 커스텀/다중 스케줄러

기본 제공되는 kube-scheduler(`default-scheduler`) 외에, 클러스터에 **여러 스케줄러를 동시에** 띄워둘 수도 있다. Pod의 `spec.schedulerName` 필드로 "이 Pod의 배정을 어느 스케줄러가 담당할지" 지정한다 (생략하면 `default-scheduler`가 담당).

```yaml
spec:
  schedulerName: my-custom-scheduler   # 이 Pod는 커스텀 스케줄러가 배정 담당
```

## 🦐 Taints and Tolerations — "밀어내기" 메커니즘

Taint는 **Node**에 붙이는 "출입 제한 표지판"이고, Toleration은 **Pod**가 들고 있는 "허가증"이다. 핵심은 **허가증(toleration)이 있다고 그 Node에 반드시 가야 하는 게 아니라는 것** — 그냥 "그 Node도 후보군에 포함될 수 있다"는 자격일 뿐이다. Taint/Toleration은 Pod를 특정 Node로 **끌어당기는(attract)** 게 아니라, tolerate 못하는 Pod를 **밀어내는(repel)** 메커니즘이라는 방향성을 꼭 기억해야 한다.

```
[Node1: taint 없음]        [Node2: taint(app=blue:NoSchedule)]
     ▲                              ▲
     │ 아무 Pod나 스케줄 가능           │ toleration 없는 Pod는 거부
     │                              │ toleration 있는 Pod는 "갈 수도" 있음 (강제 아님)
  일반 Pod                     toleration 가진 Pod
```

### Taint 걸기 / 빼기 / 확인

```bash
kubectl taint nodes node1 app=blue:NoSchedule    # taint 추가 (key=value:effect)
kubectl taint nodes node1 app=blue:NoSchedule-   # 끝에 -를 붙이면 제거
kubectl describe node node1 | grep Taints         # 현재 taint 확인
```

### Effect 3가지 — 강도가 다르다

| Effect | 새 Pod 스케줄 | 이미 떠 있는 Pod |
|---|---|---|
| `NoSchedule` | tolerate 안 하면 차단 | 영향 없음 (그대로 유지) |
| `PreferNoSchedule` | 가능하면 회피(soft) — 다른 선택지 없으면 배치될 수 있음 | 영향 없음 |
| `NoExecute` | tolerate 안 하면 차단 | tolerate 안 하면 **즉시(또는 `tolerationSeconds` 이후) 축출(evict)** |

### Toleration YAML

```yaml
spec:
  tolerations:
    - key: "app"
      operator: "Equal"      # 또는 "Exists" (이 경우 value 필드 생략, key만 일치하면 됨)
      value: "blue"
      effect: "NoSchedule"
      # tolerationSeconds: 60   # NoExecute일 때만 의미 있음 — taint 발생 후 버틸 수 있는 유예 시간
```

### ⚠️ 가장 흔한 오해 — Taint/Toleration만으로는 "강제 배치"가 안 된다

Toleration이 있는 Pod도 스케줄러 입장에서는 여전히 아무 taint 없는 다른 Node를 자유롭게 고를 수 있다. "이 Pod를 **반드시** 특정 Node에만 보내고 싶다"면 Taint/Toleration만으론 부족하고 **nodeAffinity/nodeSelector와 함께 써야** 한다. 실전 패턴: 전용 Node군에 taint를 걸어두고, 그 Node가 필요한 Pod에는 toleration(갈 수 있다) + nodeAffinity(가야 한다)를 동시에 부여 — "밀어내기(taint)"와 "끌어당기기(affinity)"를 조합해야 진짜 "전용 Node"가 완성된다.

> 💡 이미 실전에서 마주친 taint 하나: 쿠버네티스는 컨트롤 플레인 Node에 기본으로 `node-role.kubernetes.io/control-plane:NoSchedule` taint를 자동으로 걸어둔다. 일반 워크로드 Pod가 toleration 없이는 마스터 노드에 배치되지 않는 이유가 바로 이것.

## ❓ 확인 질문
1. `spec.nodeName`을 직접 지정한 Pod가 있는데, 그 Node가 이미 자원이 꽉 찬 상태라면 어떻게 될까? (힌트: 이 Pod가 Filtering 단계를 거치는지)
2. `kubectl describe pod`에서 `0/3 nodes are available: 3 node(s) had taint {...}, that the pod didn't tolerate`라는 이벤트가 보이면 뭘 의심해야 할까?
3. kube-scheduler 자체가 다운된 상태에서 새 Pod를 만들면, 그 Pod의 `status.phase`는 어떻게 될까?
4. Toleration만 있고 nodeAffinity가 없는 Pod가 있다면, 이 Pod가 반드시 taint 걸린 그 Node로 갈까?
5. `NoExecute` taint가 새로 걸렸는데, 이미 그 Node에서 돌고 있던 Pod에 `tolerationSeconds: 60`인 toleration이 있다면 몇 초 뒤에 축출될까?
6. 컨트롤 플레인 노드에 일반 Pod가 안 뜨는 이유는 정확히 무엇 때문일까?
