# 🔑 컨트롤 플레인 & 노드 핵심 컴포넌트 — 복습노트
> 2026-08-15 학습분 요약 (etcd / kube-apiserver / controller-manager / scheduler / kubelet / kube-proxy)
> 상세 내용은 [[01-클러스터_아키텍처]] 참고. 이 노트는 빠른 복습용 요약본.

## 🦐 한눈에 보기

```
                         ┌────────────── 컨트롤 플레인 ──────────────┐
   kubectl ──▶ [kube-apiserver] ◀──▶ [etcd]
                        ▲   ▲
                        │   └──────── [kube-scheduler]
                        └──────────── [kube-controller-manager]
                        └──────────────────────────────────────────┘
                        ▲
                        │  (오직 API 서버를 통해서만 통신)
                        ▼
                 ┌───────── 워커 노드 ─────────┐
                 [kubelet]        [kube-proxy]
                        └── 컨테이너 런타임(containerd 등)
```

핵심 원칙 한 줄: **모든 컴포넌트는 서로 직접 통신하지 않고, 오직 `kube-apiserver`를 통해서만 상호작용한다.**

## 🦐 요약 표

| 컴포넌트 | 위치 | 한 줄 역할 | 핵심 키워드 |
|---|---|---|---|
| **etcd** | 컨트롤 플레인 | 클러스터의 모든 상태를 저장하는 key-value 저장소 | "클러스터의 데이터베이스", 백업/복구 대상 |
| **kube-apiserver** | 컨트롤 플레인 | 모든 요청의 단일 진입점, REST API 제공 | 인증/인가, 유일한 etcd 접근 경로 |
| **kube-controller-manager** | 컨트롤 플레인 | 여러 컨트롤러(Node, ReplicaSet, Endpoint 등)를 한 프로세스로 실행 | 조정 루프(reconciliation loop), 현재↔원하는 상태 수렴 |
| **kube-scheduler** | 컨트롤 플레인 | 아직 노드가 없는 Pod를 적절한 노드에 배정 | 리소스 요구량·제약조건 고려 |
| **kubelet** | 워커 노드 | 노드별 에이전트, PodSpec대로 컨테이너가 떠 있는지 지속 확인 | 노드마다 1개씩 상주 |
| **kube-proxy** | 워커 노드 | Service 단위 트래픽을 실제 Pod로 라우팅 | iptables/IPVS 규칙 관리 |

## 🦐 컴포넌트별 한 문단 요약

**etcd** — 클러스터의 원하는 상태(Desired State)와 현재 상태(Current State)가 모두 기록되는 곳. 여기가 죽으면 클러스터 전체 상태를 잃는 것과 같아서, CKA에서 백업(`etcdctl snapshot save`)·복구(`snapshot restore`) 실습이 중요하게 다뤄짐.

**kube-apiserver** — "관문" 역할. `kubectl`이든 다른 컨트롤 플레인 컴포넌트든 kubelet이든, 클러스터의 어떤 것도 서로 직접 얘기하지 않고 반드시 API 서버를 거친다. 인증(authN)·인가(authZ, RBAC 여기서 적용)·요청 검증까지 담당.

**kube-controller-manager** — 그 자체가 컨트롤러 하나가 아니라, ReplicaSet 컨트롤러·Node 컨트롤러·Endpoint 컨트롤러 등 여러 독립적인 제어 루프를 한 프로세스로 묶어놓은 것. 각 루프는 "지금 상태를 원하는 상태로 계속 수렴시키는" 동일한 패턴으로 동작. (예: ReplicaSet의 Pod 개수 유지, Service의 Endpoints 자동 갱신이 다 여기서 나옴)

**kube-scheduler** — 새로 생성됐지만 아직 어느 노드에서 뜰지 정해지지 않은 Pod(`nodeName`이 비어있는 Pod)를 감지해서, 각 노드의 가용 리소스·어피니티·테인트 등을 고려해 최적의 노드를 배정. 배정만 하고 실제 실행은 하지 않음. (동작 원리 상세: [[02-워크로드와_스케줄링|Filtering/Scoring 단계별 정리]])

**kubelet** — 각 워커 노드에 하나씩 상주하는 에이전트. API 서버가 "이 노드에 이 Pod가 떠 있어야 한다"고 지시하면, 실제로 컨테이너 런타임에게 컨테이너를 띄우라고 지시하고 그 상태를 계속 API 서버에 보고. (컨트롤 플레인 쪽이 아니라 노드 쪽 컴포넌트라는 점 주의)

**kube-proxy** — 각 노드에서 Service의 ClusterIP/NodePort로 들어온 트래픽을 실제 대상 Pod로 전달하는 규칙(iptables 또는 IPVS)을 관리. Service가 "고정 IP처럼 보이지만 실제로는 여러 Pod로 분산"되는 동작의 실행 주체.

## 🦐 헷갈리기 쉬운 포인트 3가지
1. **kubelet ≠ 컨트롤 플레인.** kubelet과 kube-proxy는 워커 노드 소속이고, 나머지 넷(etcd/apiserver/controller-manager/scheduler)이 컨트롤 플레인 소속.
2. **스케줄러는 "배정"만 하지 "실행"은 안 함.** 실제로 컨테이너를 띄우는 건 각 노드의 kubelet + 컨테이너 런타임.
3. **모든 상태 변화는 결국 etcd에 기록되고, 그 기록에 접근하는 유일한 창구는 kube-apiserver.** 다른 컴포넌트가 etcd에 직접 붙는 일은 없음.
