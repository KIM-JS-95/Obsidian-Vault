# 클러스터 아키텍처, 설치 및 구성 (CKA 도메인 25% — CKAD 범위 아님)

> CKA 커리큘럼 세부 항목: RBAC 관리 · kubeadm으로 기본 클러스터 구성 · 고가용성(HA) 클러스터 관리 · 클러스터 인프라 프로비저닝 · kubeadm을 이용한 버전 업그레이드 · etcd 백업/복구

기초 개념(오케스트레이션, 선언적 구성 등)은 [[kubernetes|🐋 쿠버네티스 개요]] 노트에 이미 정리되어 있음. 이 노트는 그 위에서 **CKA 시험 관점의 구성요소 상세**를 다룬다.

## 🦐 전체 구조

![쿠버네티스 클러스터 아키텍처](https://kubernetes.io/images/docs/kubernetes-cluster-architecture.svg)

클러스터는 크게 **컨트롤 플레인(Control Plane)** 과 **워커 노드(Worker Node)** 로 나뉜다.
- 컨트롤 플레인 : 클러스터의 "두뇌". 전역 상태를 관리하고 스케줄링·API 처리를 담당.
- 워커 노드 : 실제 컨테이너(Pod)가 구동되는 곳.

## 🦐 컨트롤 플레인 구성요소

| 구성요소 | 역할 |
|---|---|
| `kube-apiserver` | 모든 요청이 거쳐가는 단일 진입점. REST API를 노출하며, `kubectl`을 포함한 모든 컴포넌트는 오직 API 서버를 통해서만 통신한다. |
| `etcd` | 클러스터의 모든 상태(원하는 상태 + 현재 상태)를 저장하는 key-value 저장소. 사실상 클러스터의 "데이터베이스". |
| `kube-scheduler` | 아직 노드가 배정되지 않은 Pod를 감지하여, 리소스 요구량·제약조건을 고려해 적절한 노드에 배정한다. (동작 원리 상세: [[02-워크로드와_스케줄링]]) |
| `kube-controller-manager` | 여러 컨트롤러(Node, ReplicaSet, Endpoint, ServiceAccount 등)를 하나의 프로세스로 묶어 실행. 각 컨트롤러는 "현재 상태 → 원하는 상태"로 수렴시키는 제어 루프(reconciliation loop)를 돈다. |
| `cloud-controller-manager` | 클라우드 제공자(AWS, GCP 등) 관련 로직을 클러스터 코어 로직과 분리. 온프레미스 환경에서는 없을 수도 있다. |

## 🦐 워커 노드 구성요소

| 구성요소 | 역할 |
|---|---|
| `kubelet` | 각 노드에서 실행되는 에이전트. API 서버가 지시한 PodSpec대로 컨테이너가 실행 중인지 지속적으로 확인. |
| `kube-proxy` | 노드의 네트워크 규칙(iptables/IPVS)을 관리해 Service 단위 트래픽 라우팅(로드밸런싱)을 구현. |
| Container Runtime | 실제로 컨테이너를 실행하는 소프트웨어. CRI(Container Runtime Interface) 표준을 따름 — `containerd`, `CRI-O` 등. (Docker Engine 자체는 더 이상 기본 런타임 아님, `dockershim` 제거됨) |

## 🦐 kubeadm으로 클러스터 구성 (핵심 명령)

```bash
# 컨트롤 플레인 노드 초기화
kubeadm init --pod-network-cidr=10.244.0.0/16

# kubectl 사용을 위한 kubeconfig 설정
mkdir -p $HOME/.kube
cp -i /etc/kubernetes/admin.conf $HOME/.kube/config

# 워커 노드 조인 (init 출력에 나오는 토큰 사용)
kubeadm join <control-plane-host>:6443 --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

# 조인 토큰을 잊었을 때 재발급
kubeadm token create --print-join-command
```

CNI(Container Network Interface) 플러그인(Calico, Flannel 등)은 `kubeadm init`이 자동으로 설치하지 않으므로 별도로 적용해야 Pod 간 통신이 가능해진다.

## 🦐 고가용성(HA) 클러스터

컨트롤 플레인을 여러 대로 구성해 단일 장애점(SPOF)을 없애는 구조. 두 가지 etcd 토폴로지가 있다.

- **Stacked etcd** : etcd가 컨트롤 플레인 노드와 같은 서버에서 실행. 구성이 간단하지만, 노드 손실 시 컨트롤 플레인과 etcd 멤버를 동시에 잃는 위험이 있다.
- **External etcd** : etcd를 별도 서버 클러스터로 분리. 더 견고하지만 인프라가 2배로 필요.

두 경우 모두 앞단에 로드밸런서(또는 VIP)를 두어 여러 `kube-apiserver`에 트래픽을 분산한다.

## 🦐 버전 업그레이드 (kubeadm)

업그레이드는 컨트롤 플레인 → 워커 노드 순으로, 항상 한 마이너 버전씩 진행한다 (예: 1.30 → 1.31, 1.31 → 1.32처럼).

```bash
# 1. 업그레이드 가능 여부 확인 (첫 컨트롤 플레인 노드에서)
kubeadm upgrade plan

# 2. kubeadm 자체 업그레이드 후 적용
apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm='1.31.x-*'
kubeadm upgrade apply v1.31.x

# 3. 각 노드의 kubelet/kubectl 패키지 업그레이드 (노드별로 drain → 업그레이드 → uncordon)
kubectl drain <node> --ignore-daemonsets
apt-get install -y kubelet='1.31.x-*' kubectl='1.31.x-*'
systemctl daemon-reload && systemctl restart kubelet
kubectl uncordon <node>
```

## 🦐 etcd 백업 & 복구

etcd가 죽으면 클러스터 상태 전체를 잃는 것과 같으므로, CKA에서 비중 있게 다뤄지는 실습 항목이다.

```bash
# 백업 (snapshot 저장)
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 복구 (새 데이터 디렉터리로 복원 후 etcd 재구성 필요)
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-from-backup
```
복구 후에는 `/etc/kubernetes/manifests/etcd.yaml`의 `--data-dir`를 새 경로로 바꿔줘야 static pod가 복구된 데이터를 사용한다.

## 🦐 RBAC (Role-Based Access Control)

| 오브젝트 | 범위 | 용도 |
|---|---|---|
| `Role` | 네임스페이스 단위 | 특정 네임스페이스 내 리소스 권한 정의 |
| `ClusterRole` | 클러스터 전체 | 클러스터 범위 리소스(Node 등) 또는 여러 네임스페이스 공통 권한 정의 |
| `RoleBinding` | 네임스페이스 단위 | Role(or ClusterRole)을 특정 사용자/그룹/ServiceAccount에 바인딩 |
| `ClusterRoleBinding` | 클러스터 전체 | ClusterRole을 클러스터 전체 범위로 바인딩 |

```bash
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding read-pods --role=pod-reader --user=jsung --namespace=dev

# 권한 확인 (디버깅에 자주 사용)
kubectl auth can-i list pods --as=jsung -n dev
```
