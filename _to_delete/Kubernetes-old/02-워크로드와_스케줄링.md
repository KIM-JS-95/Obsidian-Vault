## 🦐 계층 구조 한눈에 보기

```
Deployment  ─(관리)─▶  ReplicaSet  ─(관리)─▶  Pod × N
   │ 선언적 업데이트/롤백을 위해 ReplicaSet을 감쌈
                              │ 지정된 개수의 Pod를 유지(self-healing)
                                          │ 실제 컨테이너가 도는 최소 배포 단위
```

보통 실무/시험에서는 Pod나 ReplicaSet을 직접 만들지 않고, **Deployment 하나만 다루면 나머지는 자동으로 따라온다.**

## 🦐 Pod — 최소 배포 단위

- 쿠버네티스에서 스케줄링되는 가장 작은 단위. 하나 이상의 컨테이너를 감싸며, 그 안의 컨테이너들은 **같은 네트워크 네임스페이스(같은 IP, `localhost`로 서로 통신)** 와 **같은 볼륨**을 공유한다.
- 컨테이너 1개 = Pod 1개가 가장 흔한 형태지만, 로깅/프록시 등을 붙이는 사이드카(sidecar) 패턴처럼 여러 컨테이너를 한 Pod에 묶기도 한다.
- Pod는 기본적으로 **일회성(ephemeral)** 이다. Pod를 단독으로 만들면 노드 장애나 삭제 시 다시 만들어지지 않는다 — 그래서 실무에서는 거의 항상 컨트롤러(ReplicaSet/Deployment)를 통해 생성한다.

```yaml
# pod.yaml — 최소 예시
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
```

### 🦐 Pod 배포 이론 — 라이프사이클

Pod가 만들어져서 없어지기까지 거치는 단계(`status.phase`)는 5가지다.

| Phase | 의미 |
|---|---|
| `Pending` | API 서버에는 생성됐지만, 아직 노드에 스케줄되지 않았거나 이미지 다운로드 등 준비 중 |
| `Running` | 노드에 배정 완료, 컨테이너 1개 이상이 실행 중(또는 시작/재시작 중) |
| `Succeeded` | 모든 컨테이너가 정상 종료(exit 0)되고 재시작되지 않음 — 주로 Job에서 나타남 |
| `Failed` | 모든 컨테이너가 종료됐고, 그중 하나 이상이 실패(non-zero exit) |
| `Unknown` | kubelet과 통신이 끊겨 상태를 알 수 없음 (노드 장애 등) |

Pod 내부 각 컨테이너의 상태(`status.containerStatuses[].state`)는 별도로 3가지: `Waiting`(이미지 pull 등 시작 전) / `Running`(정상 실행 중) / `Terminated`(종료됨, exit code 포함).

**restartPolicy** (Pod 전체에 적용되는 재시작 정책, 컨테이너가 죽었을 때 kubelet이 취하는 동작):

| 값 | 동작 | 주 사용처 |
|---|---|---|
| `Always` (기본값) | 항상 재시작 | Deployment/ReplicaSet — 이 값이 아니면 애초에 생성 불가 |
| `OnFailure` | 비정상 종료(exit ≠ 0)일 때만 재시작 | Job (배치 작업) |
| `Never` | 재시작 안 함 | 1회성 진단용 Pod 등 |

> ⚠️ Deployment/ReplicaSet으로 만든 Pod는 `restartPolicy: Always`만 허용된다. "Pod가 계속 재시작된다"는 문제 상황이 나오면 restartPolicy가 아니라 컨테이너 자체가 크래시하고 있다는 신호로 봐야 한다 (`CrashLoopBackOff`).

### 🦐 Pod 배포 이론 — 헬스체크(Probe)

컨테이너가 "떠 있다(Running)"는 것과 "정상 동작한다"는 것은 다르다. 이를 구분하기 위한 3가지 프로브:

| Probe | 실패 시 동작 | 용도 |
|---|---|---|
| `livenessProbe` | **컨테이너를 재시작** | 데드락 등으로 응답 불가 상태에 빠진 컨테이너 감지 |
| `readinessProbe` | Pod를 **Service의 Endpoints에서 제외** (컨테이너 재시작 X) | 아직 트래픽 받을 준비가 안 된 Pod로 요청이 가지 않도록 차단 — 앞서 배운 Service의 Endpoints와 바로 연결되는 개념 |
| `startupProbe` | 계속 실패하면 컨테이너를 재시작 | 시작이 느린 애플리케이션에게 초기 구동 시간을 벌어줌 (성공 전까지 liveness/readiness는 대기) |

```yaml
    livenessProbe:
      httpGet:
        path: /healthz
        port: 80
      initialDelaySeconds: 5
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /ready
        port: 80
      periodSeconds: 5
```

### 🦐 Pod 배포 이론 — Init Container

메인(app) 컨테이너가 시작되기 **전에 순서대로** 실행되고 완료(exit 0)되어야 다음으로 넘어가는 컨테이너. 설정 파일 미리 받아오기, DB 준비될 때까지 대기하기 같은 초기화 작업에 쓴다. 실패하면 정책에 따라 재시도되며, 메인 컨테이너는 그동안 시작되지 않는다.

```yaml
  initContainers:
    - name: wait-for-db
      image: busybox
      command: ['sh', '-c', 'until nslookup db-svc; do sleep 2; done']
```

### 🦐 종료(Graceful Shutdown) 이론

Pod를 삭제하면 즉시 죽는 게 아니라: kubelet이 컨테이너에 **SIGTERM**을 보내고 → `terminationGracePeriodSeconds`(기본 30초) 만큼 대기 → 그래도 안 죽으면 **SIGKILL**로 강제 종료. 이 사이에 readinessProbe가 실패로 전환되며 Service Endpoints에서도 먼저 빠진다. (애플리케이션이 SIGTERM을 무시하도록 짜여 있으면 항상 30초 뒤에야 종료되는 문제로 이어짐 — 트러블슈팅 단골 포인트.)

### Pod 관련 명령어

```bash
# 생성/조회
kubectl run nginx-pod --image=nginx:1.27 --port=80    # 명령형으로 Pod 즉석 생성
kubectl apply -f pod.yaml                              # 선언형으로 생성/갱신
kubectl get pods                                        # Pod 목록
kubectl get pods -o wide                                 # 노드/IP까지 표시
kubectl get pod nginx-pod -o yaml                         # 전체 스펙/상태를 YAML로 확인
kubectl get pod nginx-pod -o jsonpath='{.status.phase}'    # 특정 필드만 추출 (스크립팅용)
kubectl describe pod nginx-pod                           # 상세 정보 + 이벤트(트러블슈팅 시 최우선 확인)

# 로그/접속/디버깅
kubectl logs nginx-pod                                    # 컨테이너 로그
kubectl logs nginx-pod -c <container> --previous            # 멀티 컨테이너 Pod / 재시작 전 로그
kubectl logs -f nginx-pod                                   # 실시간 tail
kubectl exec -it nginx-pod -- /bin/sh                        # 컨테이너 쉘 접속
kubectl port-forward pod/nginx-pod 8080:80                    # 로컬 8080 → Pod 80 포트 포워딩
kubectl cp nginx-pod:/var/log/app.log ./app.log                # 파일 복사
kubectl top pod                                                 # CPU/메모리 사용량 (metrics-server 필요)

# 수정/삭제
kubectl label pod nginx-pod tier=frontend                        # 라벨 추가/변경
kubectl annotate pod nginx-pod owner=jsung                        # 어노테이션 추가
kubectl edit pod nginx-pod                                          # 즉석 수정 (일부 필드는 재생성 없이 변경 불가)
kubectl delete pod nginx-pod                                         # 삭제 (그레이스풀, 기본 30초 대기)
kubectl delete pod nginx-pod --grace-period=0 --force                 # 강제 즉시 삭제 (디버깅 시에만 권장)
```

## 🦐 ReplicaSet — 개수 보장 컨트롤러

- **지정된 수(replica)의 Pod가 항상 떠 있도록 보장**하는 컨트롤러. Pod가 죽으면 즉시 새 Pod를 만들어 채운다 (self-healing).
- `spec.selector.matchLabels`로 "어떤 라벨을 가진 Pod를 관리할지" 정의하고, `spec.template`으로 "새로 만들 Pod의 모양"을 정의한다.
- CKA 시험/실무에서 ReplicaSet을 직접 만드는 일은 드물다 — Deployment가 내부적으로 자동 생성·관리한다.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

```bash
kubectl get rs                       # ReplicaSet 목록
kubectl describe rs nginx-rs         # 상세 (DESIRED/CURRENT/READY 확인)
kubectl scale rs nginx-rs --replicas=5   # 수동 스케일 (Deployment 없이 직접 조작 시)
```

> ⚠️ 헷갈리기 쉬운 포인트: `replicas` 개수를 3 → 1로 줄이면 ReplicaSet은 **아무 Pod나 골라서** 종료시킨다. 특정 Pod를 지켜야 한다면 `matchLabels` 조건에서 벗어나게 라벨을 바꾸거나 별도 전략이 필요하다.

## 🦐 Deployment — 선언적 업데이트 + 롤백

- ReplicaSet을 감싸는 상위 컨트롤러. **Pod 이미지/스펙을 바꿀 때 무중단으로 점진적 교체(Rolling Update)** 하고, 문제가 생기면 **이전 버전으로 롤백**할 수 있게 해준다.
- Deployment의 스펙을 바꾸면(예: 이미지 태그 변경) 새 ReplicaSet이 하나 더 생성되고, 기존 ReplicaSet의 Pod 수를 서서히 줄이면서 새 ReplicaSet의 Pod 수를 서서히 늘린다. 이전 ReplicaSet들은 0개로 줄어든 채 **revision history**로 남아 롤백에 쓰인다.
- 배포 전략(`spec.strategy.type`): `RollingUpdate`(기본, 무중단) vs `Recreate`(기존 Pod 전부 종료 후 새로 생성, 다운타임 있음).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1   # 업데이트 중 동시에 내려갈 수 있는 최대 Pod 수
      maxSurge: 1          # 업데이트 중 초과로 띄울 수 있는 최대 Pod 수
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

### Deployment 관련 명령어

```bash
kubectl create deployment nginx-deploy --image=nginx:1.27 --replicas=3   # 명령형 생성
kubectl apply -f deployment.yaml                                          # 선언형 생성/갱신

kubectl get deployments
kubectl get rs                          # Deployment가 만든 ReplicaSet도 함께 확인
kubectl rollout status deployment/nginx-deploy    # 롤아웃 진행 상황 실시간 확인

# 이미지 업데이트 (롤링 업데이트 트리거)
kubectl set image deployment/nginx-deploy nginx=nginx:1.28

# 스케일
kubectl scale deployment/nginx-deploy --replicas=5

# 롤백
kubectl rollout history deployment/nginx-deploy         # 리비전 목록
kubectl rollout undo deployment/nginx-deploy             # 바로 이전 버전으로
kubectl rollout undo deployment/nginx-deploy --to-revision=2   # 특정 리비전으로

# 일시정지/재개 (여러 변경을 한 번에 롤아웃하고 싶을 때)
kubectl rollout pause deployment/nginx-deploy
kubectl rollout resume deployment/nginx-deploy
```

## ❓ 확인 질문
1. Deployment의 `replicas`를 3 → 1로 줄였다가 다시 3으로 늘리면, 처음 만들어졌던 그 Pod가 그대로 살아있을까?
2. `maxUnavailable: 0`, `maxSurge: 1`로 설정하면 롤링 업데이트 동작이 어떻게 달라질까?
3. ReplicaSet을 Deployment 없이 단독으로 쓰면 안 되는 이유(=Deployment가 주는 것)는 뭘까?
4. `readinessProbe`만 실패하고 `livenessProbe`는 통과하는 Pod가 있다면, 이 Pod는 `kubectl get pods`에서 `Running`으로 보일까 아닐까? 그리고 Service는 이 Pod로 트래픽을 보낼까?
5. `initContainers`가 계속 실패하면 메인 컨테이너와 Pod의 `status.phase`는 각각 어떻게 될까?
6. 애플리케이션이 SIGTERM을 무시하도록 짜여 있으면, `kubectl delete pod`는 몇 초 만에 실제로 종료될까?
